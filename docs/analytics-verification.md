# 사용자 행동 이벤트 구현 및 검증

기록일: 2026-10-08 (Asia/Seoul)

코드·테스트·프로덕션 빌드와 새 AIT 생성까지 완료했습니다. 토스 콘솔 업로드, 지표 변경, 테스트 링크 실행, 출시 작업은 수행하지 않았습니다. 현재 출시된 앱은 사용자가 새 번들을 배포하기 전까지 기존 버전을 사용합니다.

## 공식 API와 수집 데이터

`@apps-in-toss/web-framework` 3.6.0의 `Analytics.log()`를 사용합니다. 공식 문서와 설치된 SDK의 타입 및 구현에서 지원을 확인했습니다. 설치된 SDK에서 deprecated인 `eventLog()`나 추측한 API를 사용하지 않습니다. SDK·Devtools 3.6.0과 기존 의존성 버전을 유지했습니다.

```ts
Analytics.log({
  log_name: event,
  log_type: 'event',
  params: {},
});
```

분석 함수는 네 이벤트 이름만 받습니다. 금액·이름·메모·지출 ID·사용자 ID·기기 ID·카테고리·날짜 등의 업무 데이터를 받거나 전달하지 않습니다. 앱에서 식별키 발급·조회 API를 추가 호출하지 않습니다. **공식 SDK/토스 로그 시스템은 `anonymous_key`를 기본 파라미터로 자동 포함합니다.** 빈 `params`가 익명 식별키까지 없는 전송을 의미하지는 않습니다.

공식 문서상 토스 앱 Android/iOS 5.208.0 이상에서 사용할 수 있으며, 미지원 앱 버전에서는 로그가 조용히 무시됩니다. 토스 브릿지가 없는 일반 웹 환경에서는 설치된 SDK가 동기 예외를 던지지만 저장 흐름이 이를 격리합니다. 개발 서버에서는 기존 Vite 설정대로 공식 Devtools 3.x mock을 사용합니다.

## 발생 기준과 실패 격리

| 이벤트 | 성공 기준 | 발생하지 않는 경우 |
| --- | --- | --- |
| `salary_setup_completed` | 데이터가 없는 상태에서 `setup()`의 저장 성공 | 기존 데이터 복원, 월급 편집, 중복 설정, 입력·저장 실패 |
| `expense_added` | 저장 큐의 기존 데이터에 동일 ID가 없는 지출 저장 성공 | 동일 지출 재저장, 기존 지출 수정, 저장 실패 |
| `expense_edited` | 동일 ID의 기존 지출에서 금액·카테고리·날짜·메모 중 내용이 변경되고 저장 성공 | 동일 내용 저장, 필드 순서만 변경, 빈 선택 메모의 표현 차이, 저장 실패 |
| `expense_deleted` | 저장 큐의 기존 데이터에 존재하는 지출 삭제 저장 성공 | 없는 지출 삭제, 중복 삭제, 저장 실패 |

선택 메모의 누락·`undefined`·빈 문자열은 동일 내용으로 취급합니다. 값의 변화는 이벤트 판정에만 사용하며 전달하지 않습니다. 최초 설정은 현재 저장 데이터 기준입니다. 사용자가 명시적으로 초기화한 뒤 다시 설정하면 새 설정 완료로 집계합니다. 초기화 자체나 고정지출·저축 변경은 추적하지 않습니다.

각 작업의 Repository 저장 성공 후 데이터와 `saving: false` 상태를 먼저 게시합니다. 이후 별도 Promise에서 추적 함수를 호출하고 실패를 처리합니다. 저장 Promise·순차 저장 큐는 Analytics Promise를 기다리지 않습니다. 동기 예외·비동기 거절·끝나지 않는 Promise가 사용자 오류 화면이나 저장 결과를 바꾸지 않습니다.

앱에서는 저장 성공 1건에 이벤트 API를 한 번 호출하며 전송 재시도, 영속 분석 큐, 전송 완료 표식을 추가하지 않습니다. 재실행·React 초기화·로드 재시도에서 이벤트를 재전송하지 않습니다. 서버 수집의 정확히 한 번 처리는 확인되지 않았습니다. 전송 실패나 전송 직전 종료 시 이벤트가 유실될 수 있습니다.

## 사용자 데이터 및 UI 보호

- 저장 키: `salary-survival:budget:v1` 유지
- 저장 형식: `{ version: 1, data: BudgetData }` 유지
- `BudgetRepository`, `LocalStorageBudgetRepository`, 데이터 모델·검증·계산 로직 변경 없음
- Phase 1의 버전 없는 데이터 읽기 지원 유지
- 데이터 자동 초기화·삭제·마이그레이션·별도 저장 키 추가 없음
- 기존 화면·폼·스타일·라우트 및 SDK/빌드 설정 변경 없음

테스트는 별도 메모리 저장소와 검증용 데이터에서 수행했습니다. 실제 사용자의 저장 공간을 읽거나 삭제하지 않았습니다. 기존에 있던 `docs/store-screenshots/` 파일도 변경하지 않았습니다.

## 사용자가 콘솔에서 진행할 단계

1. 워크스페이스에서 `salary-survival-plyo` 앱을 선택하고 검토한 새 번들을 업로드합니다.
2. 콘솔이 발급한 토스 앱 테스트 링크/QR로 기존 데이터가 있는 기기에서 월급·지출 복원, 추가·수정·삭제, 종료·재실행을 확인합니다. 데이터 초기화는 실행하지 않습니다.
3. 확인이 끝나면 사용자가 새 버전을 출시합니다. 샌드박스·출시 준비 단계의 이벤트는 공식 안내상 분석 집계에 제공되지 않으므로 테스트 QR만으로 서버 집계를 확정하지 않습니다.
4. 출시 후 실제 행동을 수행하고 콘솔 **분석 → 이벤트**에서 네 `log_name`의 발생 추이·최근 발생 수를 확인합니다. SDK Promise 성공만으로 수집 완료라고 판단하지 않습니다. 공식 가이드는 런칭 다음 날부터 분석 데이터를 확인할 수 있다고 안내합니다.
5. **핵심 지표 → 전환 지표 → 직접 조합하기**에서 이름이 같은 이벤트를 연결합니다. 대표 전환으로 `expense_added`(지출 기록 완료), 보조 전환으로 `salary_setup_completed`(초기 월급 설정 완료)를 제안합니다.
6. 전환 지표는 최대 3개입니다. 네 이벤트를 모두 개별 전환으로 등록할 수 없으므로 수정·삭제는 분석 → 이벤트에서 따로 확인하거나 세 번째 보조 지표로 `expense_edited OR expense_deleted`를 조합합니다. 활성 지표는 1개이며 필요하면 별도로 정의합니다. 기존 지표를 확인하고 콘솔 변경은 사용자가 결정합니다.
7. 핵심 지표 변경은 다음 날부터 적용됩니다. 핵심 지표의 차트는 전환/활성 **사용자 수**이므로 지출 **건수**와 다를 수 있습니다. 행동 건수는 분석 → 이벤트에서 확인합니다.

핵심 지표 메뉴에 아직 새 이벤트가 표시되지 않는 경우 실제 출시 버전에서 해당 행동이 수행·수집됐는지와 분석 반영 시점을 확인합니다. 이벤트 사전 등록이 필수라는 공식 근거는 확인되지 않았으므로 임의의 등록 API·설정을 추가하지 않았습니다.
